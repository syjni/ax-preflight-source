# AX Preflight 제품 갭 감사

검토일: 2026-09-29
검토 기준: 3분 데모 흐름, 실제 제품 가치, 결과 신뢰성, 장애 복구, 운영 준비도, 코드 유지보수성

## 결론

핵심 진단 엔진과 결과 계약은 제출 가능한 수준이다. 대표 검증 흐름, 실패 복구, 같은 run의 검색·근거 경로, 데이터셋 프리플라이트, 승인 기반 업무 실행, 영속 반복 실행과 단일 회사 PoC용 모델·데이터 경계·예상 비용 통제까지 구현되었다. 이번 재감사에서는 ③ 검색·근거 경로, ④ 고객 데이터 온보딩, ⑤ 반복 실행 오케스트레이션을 실제 고객 운영 기준으로 다시 분해했다.

온보딩의 두 P0를 해결했다. 첫째, 실행 전에 데이터 원본·스캔·검색 표면·평가 정보 분리를 검증하고 차단 상태에서는 runner를 호출하지 않는다. 둘째, 별도 승인 기록이 데이터셋·업무 ID·정확한 질문 해시·담당 역할·성공 기준을 모두 묶은 경우에만 `VERIFIED_BUSINESS_TASK`를 실행한다.

반복 실행의 P0도 해결했다. 최대 10개 업무를 업무별 1~5회, 총 50회까지 예약하고 배치·항목 상태를 원자적으로 저장한다. 진행률과 부분 실패를 표시하며, 현재 실행의 결과를 잃지 않는 안전 지점에서 일시정지·중단하고 실패 항목만 새 run ID로 재시도한다. 단일 프로세스에서는 프로젝트별 최근 24시간 실행 수·추정 비용, 배치 크기와 동시 실행 한도를 적용한다. 다중 API 프로세스 분산 lease·원자 quota, 실제 청구액 정산과 자동 backoff는 P1이다.

## 가치 우선순위

1. **검증된 Before→After 대표 흐름 — 완료**
   가장 강한 0/3→3/3 증거를 실행 ID 없이 재현하게 한다.
2. **실행 실패 복구 UX — 단계 3 완료**
   읽기 전용 runner, 실행 미발견, 연결 실패, 계약 불일치마다 원인과 다음 행동을 제공한다.
3. **검색·근거 경로 관측성 — 단계 4 완료**
   같은 run의 구조화 응답만으로 검색 후보, 읽은 자료, 최종 인용 연결을 순서대로 표시한다.
4. **고객 데이터 온보딩 — P0 완료**
   데이터 실행 가능성을 먼저 판정하고, 후보 질문을 담당자·성공 기준·적용 데이터셋에 묶인 승인 업무로 전환한다. 실제 고객 승인 기록 자체는 고객이 제공해야 한다.
5. **비동기 반복 실행 orchestration — P0 완료**
   여러 업무의 반복 실행을 영속 예약하고 진행률, 부분 실패, 수동 재시도, 일시정지·재개·중단을 관리한다. 단일 프로세스 추정 비용·동시성 한도까지 적용했으며 다중 worker lease와 실제 사용량 정산은 다음 단계다.

추가 긴급 조건 중 단일 회사 PoC용 로그인·프로젝트 역할·자료 및 승인 업무 격리,
로그인 시도 제한, 구성원 권한 회수·세션 종료, 해시 연결 감사 원장, 보존 검토·법적
보존, 사후 검증이 포함된 프로젝트 삭제와 PoC 평가·승인 보고서를 완료했다. 조직 tenant의
물리 격리, SSO·MFA, 암호화·키 관리, 자동 만료 실행·중앙 WORM 감사 저장소와 백업 복구는
프로덕션 차단 조건으로 남아 있다. 제출 전 외부 공개 주소의 새
세션·모바일 접속 확인도 필요하다.

### P0-ONB-1. 데이터셋 온보딩 프리플라이트 — 이번 단계에서 해결

- `GET /api/onboarding/{dataset}`이 실행 가능 여부와 차단·확인 항목을 구조화해 반환한다.
- 원본 파일 해시와 스캔 registry, 파싱 범위, 검색 가능한 문서·표, 런타임 평가 정보 누출을 검사한다.
- 후보 업무는 고객 승인이 아니므로 `WARN`으로 유지하며, 경고가 있어도 ad hoc 실행 가능 여부와 분리한다.
- `POST /api/run`은 `can_run=false`이면 `ONBOARDING_BLOCKED`로 종료하고 run 예약과 runner 호출을 하지 않는다.
- API 응답은 서버 절대 경로나 누출 표식의 원문을 노출하지 않는다.
- 공개 정적 데모도 같은 검사를 포함하며 Results Console은 실행 직전에 상태와 해결 행동을 표시한다.

### P0-ONB-2. 데이터셋 범위 업무 승인 — 이번 단계에서 해결

- `business_task_approvals.json`은 후보 catalog와 분리되며, 같은 task ID라도 승인된 데이터셋에서만 `VERIFIED`가 된다.
- 승인 기록은 담당 역할, 성공 기준, 승인 주체 역할, 승인일과 정확한 질문 SHA-256을 보존한다.
- catalog 질문이 바뀌거나 알 수 없는 task를 참조하면 API가 시작 단계에서 실패한다.
- 승인되지 않은 데이터셋의 `VERIFIED_BUSINESS_TASK`는 run 예약과 runner 호출 전에 `VERIFIED_TASK_NOT_ONBOARDED`로 차단한다.
- 공개 저장소의 기본 승인은 `CONTROLLED_DEMO`로 명시해 실제 고객 승인을 가장하지 않는다. 실제 고객 승인은 `CUSTOMER` 범위의 외부 승인 기록이 필요하다.
- 화면은 검증 업무와 후보 수, 승인 범위, 담당 역할과 승인일을 구분하며 승인 업무를 질문 원문 변조 없이 실행한다.

### P0-TRACE-2. 실패 시도를 포함한 검색 경로 — 이번 단계에서 해결

- 근거 판정에 사용하는 성공 응답 저장소는 변경하지 않고 별도의 write-once `tool-attempts` 감사 기록을 둔다.
- 성공과 실패를 실제 호출 순서로 기록하며 실패에는 구조화된 오류 코드만 남긴다.
- 요청 요약은 파라미터 이름, 검색어 글자 수, 결과 상한, 자료 ID, 필터 필드명만 보존한다.
- 검색어 원문, 필터 값, 표의 셀 값은 시도 기록과 RetrievalTrace에 저장하지 않는다.
- 같은 run의 성공 시도와 구조화 응답 순서가 맞지 않으면 trace 생성을 거부한다.
- 기존 frozen 실행은 시도 기록이 없음을 명시하고 성공 응답 기반 경로를 그대로 제공한다.

### P0-BATCH-1. 영속 반복 실행 — 이번 단계에서 해결

- `POST /api/batches`는 실행 전에 데이터셋 프리플라이트와 각 업무의 승인·후보 질문 일치를 모두 검사한다. 하나라도 틀리면 배치 디렉터리와 run을 만들지 않는다.
- 배치는 `artifacts/product_batches/<batch_id>/batch.json`에 임시 파일+원자 교체 방식으로 저장하고 각 항목은 기존 `POST /api/run` 계약을 그대로 사용한다.
- 항목별 run ID에는 배치·업무 순서·반복 순서·시도 횟수가 포함되며, 실패 재시도는 기존 결과를 덮지 않고 다음 시도의 새 run을 만든다.
- 일시정지와 중단 요청은 현재 runner를 중간에서 성공/실패로 임의 판정하지 않는다. 현재 항목의 최종 `DeliveryEnvelope`를 받은 뒤 다음 안전 지점에서 멈춘다.
- 프로세스 재시작 때 `RUNNING`이었던 항목은 `FAILED / INTERRUPTED_BY_RESTART`로 전환하고 배치를 `PAUSED`로 복구한다. 사용자가 상태를 확인한 뒤 실패 항목 재시도 또는 재개를 선택한다.
- Results Console 08 / 반복 실행은 업무 선택, 반복·시도 제한, 진행률, 항목별 상태와 run 조회, 네 제어 동작을 제공한다. 정적·fixture 화면에서는 변경 동작을 비활성화한다.
- 로컬 고객 dataset 배치는 저장된 요청자 identity로 항목을 실행하고, 매 실행마다 현재 프로젝트 권한·전달 승인·한도를 다시 확인한다.
- OWNER 지정 실행당 예상 비용을 최근 24시간 예약 사용량으로 누적한다. 이는 실제 token·청구 telemetry가 아니며 단일 프로세스에서만 원자적이다.

### P0-1. 대표 검증 흐름 단절 — 이번 단계에서 해결

- 증거: 사용 방법은 `30일`과 근거 직접 일치를 확인하도록 안내한다.
- 기존 동작: 콘솔 초기 상태에는 선택된 run이 없어 근거 검사 결과가 비어 있다.
- 기존 우회: `README.md` 또는 시연 대본에서 run ID를 찾아 07 / 조회와 실행에 붙여 넣어야 한다.
- 영향: 처음 보는 사용자가 제품의 가장 강한 증거까지 도달하지 못할 수 있다.
- 해결: 정적 스냅샷에 검증된 대표 Before/After 실행을 명시하고, 콘솔 상단에서 각 실행과 목표 섹션을 한 번에 연다.
- 안전장치: exporter가 참조 run, dataset, task, Before 충돌 보류, After 30일 답, 0/3→3/3 비교, `DIRECT_MATCH`를 모두 검증하지 못하면 빌드를 실패시킨다.

### P0-2. 외부 공개 주소 최종 확인 — 단계 6에서 진행

- GitHub Pages workflow와 정적 build는 준비돼 있다.
- 실제 공개 URL, 새 세션 접속, 모바일 네트워크 접속, 캐시 무효화 검사는 배포 단계에서 완료해야 한다.

## 제품 품질 P1

1. **고객 검증 업무 온보딩 — P0 완료**
   데이터셋 프리플라이트와 승인 계약을 연결했다. 실제 고객 환경에서는 고객이 제공한 `CUSTOMER` 승인 기록과 인증된 승인 주체를 운영 절차로 연결해야 하며, 저장소의 통제 데모 승인을 고객 승인으로 해석하지 않는다.

2. **비동기 반복 실행 orchestration — P0 완료**
   영속 상태, 진행률, 부분 실패, 실패 항목 수동 재시도와 안전 지점 제어, 단일 프로세스 추정 비용·동시성 한도를 구현했다. 다음 P1은 다중 worker lease, 자동 backoff, 실제 사용량 기반 분산 quota, 항목별 timeout·알림이다.

3. **검색 경로 관측성 — P0 완료**
   검색 후보, 실패 호출, 읽은 자료, 최종 인용 연결을 노출했다. 검색어 원문과 필터 값은 저장하지 않고 글자 수·필드명 등 축약 정보만 남긴다. 다음 P1은 단계별 소요 시간과 인용 커버리지다.

4. **실행 실패 복구 UX — 1차 완료**
   API 연결 실패, runner 미설정, run 미발견, 응답 계약 오류를 구분하고 현재 화면에서 다음 행동을 선택하게 했다. 배치 부분 실패 복구는 추가됐고, 운영 환경의 자동 timeout 복구·알림은 P1이다.

5. **근거 검사 확장**  
   현재 결정론적 값 일치·제한된 계산에서 날짜 범위, 예외 조건, 단위 변환과 문맥 조건의 보수적 검증으로 확장해야 한다.

## 프로덕션 차단 조건

다음 항목은 데모의 숨겨진 구현으로 포장하지 않고, 실제 외부 고객 데이터를 받기 전에 별도 설계·검증한다.

- 사내 IdP 기반 SSO·MFA, 서비스 identity와 계정 복구
- 조직 tenant별 dataset·run 저장소의 물리·논리 격리
- 프로젝트 역할의 정기 검토와 승인 workflow
- 전송·저장 암호화, secret 관리와 key rotation
- 명시적 retention 검토와 법적 보존은 구현됨; 자동 만료 실행, 중앙 WORM 보관, 백업 연계 삭제와 복구
- 도구별 전송 allowlist·DLP·마스킹과 공급자 정책 연계로 민감정보 승인 흐름 고도화
- 분산·네트워크 rate limit, 실제 사용량 기반 비용 quota와 abuse 방어
- 현재 로컬 해시 체인을 넘어선 변경 불가능한 중앙 접근·내보내기·삭제 감사 저장소

## 코드 품질 감사

- `results_console/src/App.tsx`가 API orchestration과 화면 상태를 함께 책임진다.
- `results_console/src/components/Portal.tsx`가 소개·사용 방법·헤더·푸터를 한 파일에 포함한다.
- `results_console/src/style.css`가 포털, 결과 콘솔, 인쇄, 반응형 규칙을 함께 가진다.
- 브랜드·데모 문구 일부가 컴포넌트에 반복된다.
- Python 제품 모듈은 계약과 결과 저장 경계가 비교적 명확하고, frozen verifier가 비변조를 검사한다.
- 반복 실행은 `ax_product/batches.py`에 모델·저장소·상태 머신을 모으고 기존 단일 run 실행 함수를 재사용해 결과 계약을 이중 구현하지 않는다.
- 반복 실행 화면은 `BatchPanel.tsx`가 선택·polling·제어 상태를 소유해 `App.tsx`의 기존 단일 실행 흐름과 분리한다.
- 모델·전달 경계·예상 비용 계약은 `ax_product/execution_control.py`, 영속 상태와 역할 검사는 `access_control.py`, 통합 실행 게이트는 `api.py`로 분리한다.
- `ExecutionControlPanel.tsx`가 OWNER 설정과 전 구성원의 상태·사용량 표시를 담당하고, `RunControls`와 `BatchPanel`은 통제 결과만 소비한다.

위 프런트 구조는 기능 동결 후 단계 5에서 동작 변경 없이 분리한다. 기능 구현과 대규모 리팩터링을 같은 커밋에 섞지 않는다.

## 첫 대표 흐름 P0의 완료 조건

- 공개 정적 스냅샷에 검증된 대표 사례가 포함된다.
- Before 버튼이 충돌로 보류된 대표 실행을 연다.
- After 버튼이 30일 답변과 `DIRECT_MATCH` 근거 검사로 이동한다.
- 사용자는 run ID를 입력하지 않아도 된다.
- 1440, 1024, 768, 390, 320px에서 버튼과 상태가 깨지거나 가로로 넘치지 않는다.
- exporter drift 검사, 컴포넌트 테스트, 전체 테스트, typecheck와 build가 통과한다.
- frozen v3·v4 파일과 기존 감사 기록은 수정하지 않는다.

## 온보딩 프리플라이트 P0의 완료 조건

- 정상 데이터셋은 `READY` 또는 `REVIEW_REQUIRED`로 실행 가능하다.
- 원본 해시·파일 registry 불일치는 `BLOCKED`가 된다.
- 차단된 데이터셋은 run 디렉터리를 만들거나 runner를 호출하지 않는다.
- 경고와 차단을 화면에서 다른 의미로 표시하고 해결 행동을 제공한다.
- 1440, 768, 390, 320px에서 가로 넘침 없이 검사 5개가 읽힌다.
- 정적 snapshot, Python·컴포넌트 테스트, typecheck와 build가 통과한다.

## 업무 승인 P0의 완료 조건

- 승인 기록은 후보 catalog와 분리되고 데이터셋·task ID·질문 해시에 고정된다.
- 승인 질문 drift, 중복 승인, 알 수 없는 task는 시작 전에 거부된다.
- 승인되지 않은 데이터셋에서는 같은 task ID도 검증 업무로 실행되지 않는다.
- runner에는 승인된 catalog 질문만 전달되며 공개 요청은 검증 업무에 임의 질문을 보낼 수 없다.
- 화면과 정적 데모는 `CUSTOMER`, `CONTROLLED_DEMO`, 미승인 후보를 명확히 구분한다.
- Python·컴포넌트 테스트, typecheck, build와 폭별 화면 검증이 통과한다.

## 반복 실행 P0의 완료 조건

- 한 배치가 최대 50개 실행을 넘지 않고 중복 업무 ID를 거부한다.
- 완료·부분 실패의 집계와 진행률이 항목 상태에서 계산되며 저장본과 API 응답이 일치한다.
- 일시정지·중단 요청 중인 실행은 최종 결과를 보존하고 다음 대기 항목을 시작하지 않는다.
- 실패 항목만 최대 시도 횟수 안에서 새 run ID로 재시도하며 성공 항목을 다시 실행하지 않는다.
- 재시작 중이던 실행은 성공으로 간주하지 않고 실패·일시정지 상태로 복구한다.
- 정적 데모에서는 배치 변경을 허용하지 않고, 라이브 화면은 1440, 1024, 768, 390, 320px에서 가로로 넘치지 않는다.
- Python·컴포넌트·계약 테스트, typecheck, build와 frozen v3·v4 비변조 검증이 통과한다.
